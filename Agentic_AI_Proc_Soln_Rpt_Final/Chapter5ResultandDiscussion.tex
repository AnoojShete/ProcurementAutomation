\section{Sample Code (Main Logic)}\label{sec:code}
Three excerpts of the implementation follow, unchanged except for removed log lines (marked ``\ldots'').

\paragraph{Confidence gate.} The worker discounts each field's extraction confidence $c_f$ by the quality $q \in [0,1]$ of the text it was read from, and combines the field scores with fixed weights $w_f$ (total 0.30, vendor name 0.20, classification 0.15, document number 0.15, date 0.10, line items 0.10):
\begin{equation}
s_f = c_f \cdot q, \qquad S = \frac{\sum_{f \in F} w_f\, s_f}{\sum_{f \in F} w_f}, \qquad \text{review if } S < \theta,
\label{eq:confidence}
\end{equation}
where $F$ excludes line items when a document has none, and $\theta$ is 0.8 or a per-vendor threshold learned from reviewers' corrections. Listing~\ref{lst:confidence} shows the implementation.

\begin{lstlisting}[caption={[Confidence scoring and the review gate]Confidence scoring and the review gate (document-vendor-agent, \texttt{confidence.py})}, label={lst:confidence}]
def build_confidence_scores(classification_confidence, field_confidences, text_quality):
    scores = {"classification": round(classification_confidence * text_quality, 3)}
    for field_name, conf in field_confidences.items():
        scores[field_name] = round(conf * text_quality, 3)
    return scores

WEIGHTS = {
    "total": 0.30, "vendor_name": 0.20, "classification": 0.15,
    "document_number": 0.15, "document_date": 0.10, "line_items": 0.10,
}
OPTIONAL = {"line_items"}

def overall_confidence(confidence_scores):
    scores = {k: v for k, v in confidence_scores.items() if not (k in OPTIONAL and not v)}
    if not scores:
        return 0.0
    weights = {k: WEIGHTS.get(k, 0.1) for k in scores}
    return round(sum(scores[k] * w for k, w in weights.items()) / sum(weights.values()), 3)

def needs_review(overall, threshold=None):
    return overall < (load_threshold() if threshold is None else threshold)
\end{lstlisting}

\paragraph{Race-safe stock reservation.} A short-lived Redis lock per SKU guards the check-and-decrement, while the reservation itself is stored in PostgreSQL. Each acquisition uses a fresh token so that a retry can never release another request's lock (Listing~\ref{lst:reserve}).

\begin{lstlisting}[caption={[Stock reservation under a Redis lock]Stock reservation under a Redis lock (approval-inventory-agent, \texttt{inventory\_service.py})}, label={lst:reserve}]
async def reserve_stock(db, redis_client, sku, request_id, quantity) -> bool:
    lock = InventoryLock(redis_client, ttl=10)  # 10s safety TTL, released in ms
    lock_token = str(uuid.uuid4())              # unique per acquisition
    acquired = await lock.acquire(sku, lock_token)
    if not acquired:
        return False
    try:
        # Re-check availability inside the lock
        item = (await db.execute(select(Inventory).where(Inventory.sku == sku))).scalar_one_or_none()
        if not item or item.available_quantity < quantity:
            return False
        item.available_quantity -= quantity
        item.reserved_quantity += quantity
        await db.commit()
        return True
    finally:
        await lock.release(sku, lock_token)     # always release, even on failure
\end{lstlisting}

\paragraph{Verified, replay-safe signature callback.} The webhook is not JWT-authenticated, because the provider has no platform account. It is trusted only if an HMAC-SHA256 signature over the canonical JSON body matches, compared in constant time, and a provider event ID is accepted only once (Listing~\ref{lst:webhook}).

\begin{lstlisting}[caption={[HMAC verification and replay protection]HMAC verification and replay protection (contract-risk-agent, \texttt{webhook\_service.py})}, label={lst:webhook}]
def verify_signature(payload: dict, signature: str) -> None:
    canonical = json.dumps(payload, sort_keys=True, separators=(",", ":")).encode("utf-8")
    expected = hmac.new(settings.esign_webhook_secret.encode("utf-8"), canonical, hashlib.sha256).hexdigest()
    if not hmac.compare_digest(expected, signature):
        raise WebhookSignatureError("webhook signature verification failed")

async def mark_contract_signed(db, kafka_producer, contract_id, signed_by, signed_at, provider_event_id, ...):
    existing = await db.get(ProcessedWebhookEvent, provider_event_id)
    if existing is not None:
        raise WebhookReplayError(f"webhook event {provider_event_id} already processed")
    contract = await db.get(Contract, contract_id)
    ...
    contract.status = "signed"
    db.add(ProcessedWebhookEvent(...))   # recorded in the same transaction as the status change
\end{lstlisting}

\section{Testing}
Testing was carried out at three levels: unit tests for each service and for the shared code, end-to-end tests through the gateway against the running system, and black-box probes of externally visible behaviour. Every defect fixed received a regression test, and each such test was checked by reverting the fix and confirming that it fails.

\subsection{Unit Testing}
Each service has its own pytest suite, run inside that service's Docker image with the source mounted (\code{./scripts/test-service.sh all}). The suites test logic, schemas, API behaviour and the wiring of every enforced business rule (each rule is set to two values and the test checks that behaviour changes). On 25 October 2026, after the extensions of Section~\ref{sec:extensions}, the replacement of the risk model by a deterministic scorecard and the retrieval-augmented assistant, all 1,282 tests passed, with none failing or skipped (Table~\ref{tab:unit}). A further suite tests the shared code and configuration: the event outbox and dead-letter handling, the request state machine, Kafka permissions against the code, log redaction, correlation IDs, e-mail approval actions, the business-rules registry and the refusal of published secrets in production mode. It passed 183 tests; 4 tests of the assistant's live script were skipped because they need a running language model.

Integration exposed defects that unit tests could not, which were fixed in the shared configuration: the gateway did not strip the API prefix (every route returned 404), the broker advertised an unreachable address, UUID columns were typed as strings, Alembic version tables of two services collided, and ClamAV's slow start blocked the services that depended on it.

\subsection{Security and Dependency Checks}\label{sec:deps}
Every service image was audited for known vulnerabilities with \code{pip-audit}, and the frontend with \code{npm audit}. Upgrading the web framework (FastAPI~0.148, Starlette~1.9) and the libraries that parse uploaded files (Pillow~12.3, pdfminer.six, Docling~2.140) reduced the findings from 302 to 152; the remainder are in the model-tracking server, which is not exposed, in parts of the OCR engine that the system does not call, and in test tooling. Started in production mode with the published default secrets, every service refuses to start; with new secrets, every service and worker starts (BB13). A full backup of the database and document store was restored into separate containers with identical record counts.

\section{Evaluation of the Models}\label{sec:eval}
Each model was compared with a simple baseline on data it was not trained on, and each decision rule for keeping a model was fixed before the comparison was run. All training and test data is synthetic except the CUAD contracts, so these results compare methods on controlled data; they do not predict accuracy on an organisation's real documents or vendors.

\subsection{Document Classification}
The classifier was trained on 861 of 1,260 generated documents (clean, OCR-noise, missing-title and \emph{other} paperwork), with 252 for validation and 252 for testing. A second test trained on 870 documents without one invoice layout and two kinds of \emph{other} paperwork, and tested on 390 documents of exactly those kinds. Table~\ref{tab:clf} shows that the shipped router (the model when it is at least 60\% confident, otherwise keywords) classified every test document correctly, against a macro-F1 of 0.912 and 0.844 for keywords. The keyword classifier was weakest on documents with no title (0.847 and 0.602). Because both test sets share the generator's vocabulary, perfect scores here mean the model learned these templates, not that it would be perfect on real documents.

\subsection{Field Extraction}
Extraction was measured against ground truth on 15 generated PDFs and 6 generated images, each image also tested as rotated (4\textdegree), noisy and half-resolution copies (24 image variants). Every field of every PDF was correct, but only 47\% of image fields without preprocessing and 49\% with deskewing and upscaling (Table~\ref{tab:extract}). Preprocessing helped on original and rotated images (47\% to 53\%) but hurt on noisy ones (47\% to 44\%). Image extraction is therefore the weakest part of the pipeline; this is why low-confidence documents go to review, and why OCR quality discounts every field's confidence (Equation~\ref{eq:confidence}).

\subsection{Clause Extraction}
The Legal-BERT model and the regular-expression rules were compared on the 102 contracts of CUAD's test split, real commercial contracts annotated by lawyers; a clause counts as found when the returned passage overlaps an annotated span. The model beat the rules on all three clause types (Figure~\ref{fig:clauses}), most clearly on expiration dates, which in CUAD are usually written relative to another date (``five years from the Effective Date'') and so defeat the date rules. On 60 contracts generated from the project's own templates, both methods read every value correctly. The model was kept as the primary extractor under a rule fixed in advance (beat the rules on at least two of the three clauses and read every template value). Its cost is speed: a median of 17 seconds per contract on a CPU.

The same model was tested on eight obligation categories of CUAD for contract-obligation tracking (Section~\ref{sec:extensions}), against regular-expression rules. It was adopted only where its F1 was higher and it also read every value from the platform's own templates: for licence limits (0.44 against 0.41) and termination for convenience (0.74 against 0.25). For audit rights (0.46 against 0.39) and the liability cap (0.71 against 0.37) its F1 was higher, but it missed values in the templates, so the rules remain primary; for warranty duration and insurance the rules scored higher. Recall is low for both methods on several categories because CUAD annotates long clauses that a single extracted passage rarely overlaps. Answering the eight questions takes about 52~s per contract on a CPU, which is why obligations are read in the background after signature. When the model abstains on a contract (its no-answer score is higher), the rules supply the value, which happened on one live contract during testing.

\subsection{Licence-Usage Anomaly Detection}
The anomaly model was evaluated on 600 simulated licences (seed 2026), 30\% of which follow an anomalous pattern (gradual decline, sudden drop-off or abandonment) while the rest are steady, have weekend dips or are stable at low use. The licences were split 360 / 120 / 120 for training, validation and testing. Figure~\ref{fig:licence} compares the shipped model with three alternatives on the test set. Scale-free features (utilisation and retention ratios rather than raw seat counts) raised the ROC-AUC from 0.849 to 0.954, and both are far above the earlier model trained on only five licences (0.659) and above ranking by low utilisation alone (0.687), which is what a flat inactivity rule does. The thresholds were chosen on the validation set: at the ``anomalous'' threshold (0.39) the test precision was 0.83 and the recall 0.69; at the ``watch'' threshold (0.34) they were 0.79 and 0.83. Abandoned licences were always flagged and sudden drop-offs 87\% of the time, but gradual declines only 36\% of the time, while 4--10\% of the normal licences crossed the anomalous threshold. The grace period and human approval exist for exactly these false positives.

\subsection{Vendor Risk Scoring}
The platform first scored vendor risk with a Random Forest, which is described here because its evaluation informed the replacement. The risk model was evaluated on 2,000 synthetic vendors (360 with an incident), split 1,600 / 400. The incident labels were drawn from a known formula of the six features plus random noise, so even a perfect model cannot exceed the ROC-AUC of that formula, 0.739. The Random Forest reached 0.715 (0.726 with 20\% of the values missing), close to that ceiling, with an accuracy of 0.72 at a threshold of 0.5. More importantly for its use, the bands are ordered by real incident rate (Figure~\ref{fig:bands}): 6.5\% of Low-band vendors, 20\% of Medium and 40.3\% of High had an incident. The most important features were on-time delivery (0.349), financial stability (0.210) and tenure (0.207). Twelve hand-written red-team profiles, including a perfect vendor with a cancelled GSTIN (forced High by the override), a vendor with no data on file (Medium, never High) and vendors with partial data, all received the expected band.

The Random Forest has since been archived and replaced by a deterministic scorecard (Section~\ref{sec:extensions} and Figure~\ref{fig:scr-vendor}), because the platform must explain and reproduce every risk decision. Its properties were verified rather than its accuracy: every stored score replayed to the same SHA-256 snapshot, points always summed to the total, a sanctioned vendor was forced to High by its override, and a vendor with incomplete checks was never reported as Low. The scorecard has not yet been evaluated against incident outcomes, so no accuracy figure comparable to the Random Forest's is claimed. In the demonstration environment most external sources are unreachable, so most vendors are rated provisional.

\subsection{Retrieval-Augmented Assistant}\label{sec:assistant}
The assistant was evaluated with sixteen questions whose answers are known from the contract templates and the demonstration data (\code{tests/e2e/chatbot_eval.py}, \code{docs/results/chatbot-eval.md}): six about contract clauses and rules (for example the SaaS uptime commitment and service credit, the liability cap of professional-services contracts, who approves a request above \Rs 5,000), four about current records (pending approvals, a vendor's risk rating, licence usage, a requester's latest request), a follow-up question, a question about a vendor with no contract, two attempts by a requester to see data outside their access (bank details, licence seats), a greeting and an off-topic question. An answer counts as correct when it contains the expected facts and none of the forbidden ones; the count of pending approvals is compared with the live value. As first merged, the assistant answered none of the questions (an outdated call signature made every reply an error, and its index was empty). After the changes---indexing contract clauses, documents, rules and current records with per-chunk access, retrieving before every answer, and answering only from the retrieved passages without function tools---all sixteen answers were correct on three consecutive runs, with a median response time of about two seconds on a laptop CPU (Figure~\ref{fig:scr-assistant} shows one answer). Two design decisions mattered most for the small 3-billion-parameter model: splitting contract clauses into single-obligation chunks (it had reported an insurance amount as a liability cap when both shared a passage), and writing rule values and totals as sentences rather than JSON. The evaluation is small and uses the platform's own generated data, so it shows that the pipeline is grounded and respects access, not how it would perform on an organisation's documents.

\subsection{Calibrating the Document Review Gate}\label{sec:gate}
The review gate of Equation~\ref{eq:confidence} sends a document to a person when its weighted confidence is below 0.8; how many errors that threshold lets through was unknown. A controlled experiment measured it and asked whether evidence from the organisation's records---the vendor master, the open purchase orders and earlier invoices---allows more documents to skip review at a fixed error rate.

\paragraph{Data.} A seeded generator produced a vendor master of 100 vendors (each with a GSTIN, bank details and a currency, with invoice volume following a Zipf-like distribution), 1,649 purchase orders and 3,000 invoices against them. Of the invoices, 29.8\% carry one injected business error: a unit price or quantity above the order, a resubmitted earlier invoice, a look-alike vendor name, changed bank details, a reference to another vendor's order, a wrong GSTIN, or a total that does not equal subtotal plus tax. The invoices were rendered as text PDFs (55\%) or as clean, mildly degraded and heavily degraded scans, and were read with the production extraction code. An invoice counts as \emph{correct} when its vendor, total, currency and invoice number were read correctly and it carries no business error; 59.9\% of invoices are correct.

\paragraph{Systems.} B0 is the current rule (confidence $\ge$ 0.8 and no forced-review flag). B2 accepts an invoice when every record check passes (vendor matched, order matched, no duplicate, bank details and GSTIN as on file). B1 and P are calibrated gates: a logistic-regression or gradient-boosting model estimates the probability that an invoice is correct, from document evidence only (B1) or from document and record evidence (P), and the acceptance threshold is chosen with Learn-then-Test~\cite{angelopoulos2021ltt} so that the error rate among accepted invoices is at most $\alpha$ with probability at least $1-\delta$ ($\delta = 0.1$). All systems were evaluated on 20 random splits in which the training, calibration and test sets contain different vendors.

\paragraph{Results.} Table~\ref{tab:gate} gives the main result. The current rule accepts 41\% of invoices, but 6.8\% of the accepted ones are wrong, and accepting whenever every record check passes is worse (12.8\%). Record evidence improves the ranking of invoices substantially: the area under the ROC curve rises from 0.74 with document evidence alone to 0.95 with record evidence, and removing the purchase-order match, the largest contributor, lowers it to 0.83. Nevertheless, no calibrated gate could certify an error budget of 2\% or 5\% with a useful share of invoices: among the best-ranked invoices about 5\% remain wrong, and Learn-then-Test correctly refuses to accept what it cannot certify. Inspection of these invoices showed that most were resubmitted duplicates with a new invoice number. The production duplicate check requires the two numbers to be at least 85\% similar, so it misses this case, and the order still has quantity left, so the three-way match passes too. Adding a duplicate check that ignores the number---equivalent to setting one business rule to zero---lets 12\% of invoices through at a 2\% budget and 35\% at a 5\% budget.

\paragraph{Limitations.} The invoices, records and error rates are synthetic, from a single generator. The second gate was defined after inspecting the results and must be confirmed on a new seed. Vendor-disjoint splits violate the exchangeability that Learn-then-Test assumes, which may explain violation rates above $\delta$ in some settings. External validity on public invoice datasets has not been tested.

\section{Discussion}
The results support the design in three ways. First, the agents work together as intended: a request or document passes through all five services without manual steps, and the outbox, retries and state machine keep each step consistent when events arrive late or twice. Second, each trained model earned its place against a simple alternative on held-out data under a decision rule fixed in advance: the classifier and Legal-BERT replaced rules only because they beat them, and the licence model was redesigned after its first version separated the usage patterns poorly. Third, the controls that matter most in a financial process---fail-closed scanning, dual control of bank details, role checks, replay protection, session revocation and refusal of default secrets---were verified by black-box probes against the running system.

The results also expose the system's limits. Image extraction is weak (49\% of fields correct), so scanned documents depend on review. The licence model misses most gradual declines and flags some normal licences, and a retrained model moved one demonstration licence just below its threshold; its proposals must therefore stay subject to approval. The classifier and risk-model figures come from synthetic data whose structure the models can learn; only Legal-BERT was evaluated on real documents, and those are US commercial contracts. Finally, the review-gate experiment shows that the confidence rule in use lets through 6.8\% wrong invoices among those it accepts, more than any of the error budgets studied, and that the limiting factor is a gap in one check rather than in the models: record evidence makes risk-controlled automation possible only once duplicate resubmissions are caught.
