## Components

| Component | Role |
|---|---|
| **Browser** (React SPA) | One page per item, role-based navigation, the admin Control Panel |
| **nginx gateway** (:8080) | Serves the app, proxies `/api/<prefix>` to the owning service, rate limits, security headers, correlation id, 25 MB upload cap |
| **document-vendor-agent** (8001) + worker | Intake, virus scan, MinIO, document pipeline, vendors, drop folder, Control Panel data |
| **approval-inventory-agent** (8002) + Temporal worker | Requests, approval workflows, authority, budgets, inventory, licences, RFQs, invoice ledger |
| **contract-risk-agent** (8003) + Temporal worker | Contracts, e-signature, renewals, obligations, vendor risk and clearance |
| **notification-agent** (8004) | Consumes 17 event topics, editable email templates, in-app feed |
| **auth-service** (8005) | Accounts, sessions, roles, business-rules engine |
| **chatbot-agent** (8006) | Retrieval-augmented assistant |
| **Kafka (Redpanda)** | 23 topics; each service has its own login and may use only its own topics |
| **Temporal** | Durable workflows: approval SLAs and reminders, contract renewals |
| **PostgreSQL** | Shared database; each service migrates its own tables |
| **MinIO** | Original documents |
| **Redis** | Idempotency keys, inventory reservation locks |
| **External** | ClamAV, Mailpit/SMTP, Ollama, Frankfurter (FX rates), Razorpay IFSC, HaveIBeenPwned, OpenSanctions |

## Communication

| Channel | Used for |
|---|---|
| HTTP/REST through the gateway | Browser → services (JWT bearer token) |
| Kafka events | Service → service hand-offs (`document.classified`, `approval.decided`, `contract.signed`…); written to an outbox in the same transaction as the change |
| Direct HTTP inside Docker | Four synchronous calls: invoice matching, the assistant reading data, minting email-approval links |
| Temporal gRPC | Starting and signalling workflows |
| SQL | Each service to the shared Postgres |
| HMAC-signed webhook | External e-signature callback (`/api/webhooks/esign`) |

## Data flow (one document)

1. A document arrives and is scanned by ClamAV, stored in MinIO and recorded;
   `document.ingested` is published with the row.
2. The worker reads, classifies and validates it and publishes `document.classified`.
3. A quote becomes a purchase request (`approval.requested`); a Temporal
   workflow waits for each approval level (`approval.decided`).
4. After the final approval a contract is generated and sent for signature
   (`contract.generated`); signing publishes `contract.signed` and the request
   moves to *ordered*.
5. notification-agent emails the right person at every step.
