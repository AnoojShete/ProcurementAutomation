Open with the problem (1 min)

Buying software and hardware in a company is a chain of hand-offs: someone retypes an invoice, chases an approver, drafts a contract, waits for a signature, then checks the invoice against the order by eye. It is slow, and the risky cases — a fake invoice, a changed bank account, an unreliable vendor — are easy to miss. We built five cooperating services ("agents") that carry a document from arrival to a matched payment, and bring a person in only where a decision is needed.

Architecture in one picture (2 min)

Open project-flow.html and walk top to bottom: sources → gateway, virus scan, storage → document intelligence → "confident enough?" → the procurement agents and the request lifecycle → notifications → shared services. Points to make:

Agents, not one app

Document & Vendor, Approval & Inventory, Contract & Risk, Notification, Auth — each owns its data and reacts to the others' events.

Nothing gets lost

Events are saved in the same transaction as the change (outbox), retried, and parked in a dead-letter queue if they still fail.

Long processes survive restarts

Approvals, renewals and reminders are Temporal workflows with timers.

Be upfront about

Prototype, not production

  • All data is synthetic; ML is not measured on real company data.
  • Photos / low-quality scans read poorly (49 % of fields); they go to review.
  • Built-in e-sign seal is tamper-evident (SHA-256), not a keyed signature.
  • CI builds images but doesn't run tests yet; Kafka has no TLS; single machine.

Not built yet

  • Clause extraction with a model (rules today), sanctions screening.
  • Licence anomaly model needs tuning.
  • Notification retry / dead-letter.
  • Calibrated automation gate — the research plan.

Likely questions

Why "agentic" and not just microservices?

Each agent owns a goal and decides on its own — classify, route, reclaim a licence, flag a vendor — coordinating through events, and hands off to a person when unsure.

Where is ML used?

OCR and layout (PaddleOCR, Docling, LayoutLMv3 cross-check), vendor risk (random forest), licence anomalies (IsolationForest + SHAP), fuzzy vendor matching. Rules where it must be predictable: approval tiers, dual control.

Why not an LLM for everything?

Cost, speed, determinism and audit: a small model with reasons, or a rule with a change history, is easier to defend to an auditor.

Why Kafka, Temporal, one Postgres?

Kafka so agents don't call each other and can be down independently; Temporal for processes that run for days; one Postgres to keep a four-person project simple, each service owning its tables.

How are logins protected?

argon2id hashes, lockout, rate limits, email confirmation, single-use expiring links, a refresh cookie JavaScript can't read; identity always from the token, never the request body.

Is it production-ready?

No — a working, tested prototype with production patterns. Next: tests in CI, real secrets, dependency upgrades, TLS, real e-sign provider.
